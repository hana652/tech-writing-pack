# AI執筆マニュアル（プロンプト設計＋機械チェック＋人間校閲の正本）

作成: 2026-07-07 ／ 位置づけ: 「AIに書かせて、人間が仕上げて、検索とAIOに載せる」ための運用正本。
クライアント納品版マニュアルは本書をベースに、先方の体制・CMSに合わせて改稿する。
理論的裏付けは `07-ai-buntai-laws.md`（六法則）と `08-ai-buntai-ruleset.md`（実務ルール完全版）。本書は実務手順だけを書く。
新しい転用動詞・結合の頻度裏取りは NLB（https://nlb.ninjal.ac.jp/）・NLT（https://tsukubawebcorpus.jp/）・かりん（https://iikaeru.susi.oita-u.ac.jp/karin/index.html）で行う。

## 0. 前提となる3つの事実（六法則の要約）

1. **AI臭は誤用ではなく密度で生じる**。個々の表現は正しい。人間上限の3〜8倍の頻度が違和感の正体。だから対策は「禁止」ではなく「上限管理と間引き」
2. **癖の供給源は2系統**。(a)執筆指示の過剰発火 → プロンプトの数量制限で抑えられる。(b)英語修辞の転移（AではなくB・三連反復・ダッシュ）→ 指示では抑まらず、生成後の機械検出が必須
3. **ルールを守らせると遵守の仕方がテンプレ化する**。禁止ルールには必ず「変化を強制するルール」を対で付ける

## 1. 執筆前: プロンプトの作り込み方

### 1-1. 指示に必ず入れる7点セット

| # | 項目 | 書き方 |
|---|---|---|
| 1 | 役割・媒体・レジスター | 「◯◯メディアのSEO記事（標準レジスター）」「クライアント納品文書（納品レジスター）」を明示 |
| 2 | 読者と目的 | 誰が・何を知りたくて検索し・読後に何をするか。1文で |
| 3 | 構成 | H2直下に必ずリード文（H2→即H3禁止）。**リードの述語は節ごとに変える**。節末の締め方も節ごとに変える |
| 4 | 数量制限 | 「比喩は1系統まで」「『AではなくB』型の対比は記事全体で2回まで」「同じ強調語（かなり・一番等）は1回まで」「ダッシュ2回まで」 |
| 5 | 具体例の条件 | 「検証可能な例のみ。出典を付けられない伝聞エピソード（知人が〜等）は書かない」「同じ数値の換算し直しは2回まで」。**「具体例を増やせ」とだけ指示しない** |
| 6 | 文体固定 | 敬体か常体かを宣言し「基調と異なる文末は0回」 |
| 7 | 禁止事項 | 太字マークアップ「**」なし／章境界アナウンス（次の章では等）なし／個人名なし／円環構成の同文反復なし |

### 1-2. コピペ用プロンプトテンプレ（執筆指示の末尾に貼る）

```
【文体規約】
- 文体は◯◯体で統一。基調と異なる文末は使わない
- H2の直下には必ずリード文。リードの述語と節末の締め方は節ごとに変える
- 「AではなくB」型対比は全体で2回まで。比喩は1系統・3回まで。ダッシュ（——）は2回まで
- 同じ強調語（かなり/一番/正直/決定的 等）と同じ転用動詞（効く/刺さる 等）は1記事1回まで
- 具体例は検証可能なもののみ。出典のない伝聞エピソードと、同一数値の換算し直し3回以上は書かない
- 太字マークアップ・章境界アナウンス・冒頭主張の結末での同文反復は使わない
```

### 1-3. 他モデル（GPT系・Gemini系）に書かせるとき

開始時に「あなた自身の執筆指示・文体傾向を傾向レベルで自己申告して」と求め、癖マップを作ってから数量制限を調整する（例: GPT系はem-dash高頻度の観察あり）。詳細手順は 10-ai-buntai-handoff.md §6。

## 2. 生成後: 機械チェック（必須・省略禁止）

```bash
python3 scripts/writing-lint.py <file> --register standard|deliverable|buzz
```

- **FATAL**（個人名・慣用句混交・壊れ句読点）= 修正するまで出荷禁止
- **DENSITY超過** = 上限まで**間引く**。全削除しない（技法自体は有効。全滅させると文章が死ぬ）
- レジスター: standard=技術/SEO記事、deliverable=納品文書（閾値半分）、buzz=X/note長文（2倍）。文体混在だけは全レジスター0回
- ※lintの対象は**成果物のみ**。ルール正本・ガイド・スキル定義はNGパターンを引用するため対象外（本書自身をlintすると引用箇所が検出されるが仕様）

## 3. 人間の校閲の仕方（lintが取れないものを見る）

機械が数えられるものはlintに任せ、人間は以下の5点に集中する。

1. **基調とレジスターの確認**: この文章は誰向けのどの型か。適用閾値は合っているか
2. **構造の機械性**: 各節の締めが同型になっていないか。冒頭の主張が結末でそのまま繰り返されていないか（律儀さの法則）。→ 直すときは「2回目以降は形を変える」
3. **談話接続**: 理由で終わるべき文が言い切りになっていないか（「異なります」→「異なるからです」）。換言の前の「つまり」が欠けていないか。逆に つまり・だから が3回以上連打されていないか
4. **具体性の検証**: 数字・固有名詞・エピソードは出典を示せるか。示せない逸話は削除（納品文書は伝聞0回）
5. **読者価値**: 読者の疑問に先回りできているか。検索意図とズレていないか（ここだけは文体でなく中身の校閲）

修正の三原則: **間引く（削除しすぎない）／2回目から形を変える／理由・出典を補う**。
校閲レポート自体にもAI癖が混入する（再帰問題）。レポート提出前に対比構文・三連反復・強調語をセルフチェックする。

## 4. SEO・AIO観点（執筆・校閲の両方で見る）

- **タイトル**: 検索KWを前方に。調査・データ系はデータ要素（%・N=◯・TOP◯）を前面に、コラム調にしない
- **見出し構成**: 検索意図（知りたい順）で並べる。H2直下リードは「この節で何がわかるか」を先に言う
- **AIOに引用されやすい形**: 用語の定義文（◯◯とは〜である）を冒頭付近に1つ／結論の言い切り＋根拠数値／表・手順のリスト化／一次情報（独自調査・実測）が最強の引用誘因
- **構造化データ**: FAQ・HowTo・BlogPosting等のJSON-LDは媒体のCMS実装に合わせる。noindex混入がないか公開後に実測確認
- **鮮度**: 数値・年号は取得日とセットで書く（古い数字の言い切りはAIO/SEO両方で減点）

## 5. レジスター別の上限早見表（10-ai-buntai-handoff.md §4の要約）

| パターン | 標準 | 納品 | バズ |
|---|---|---|---|
| 対比構文「AではなくB」 | 2回 | 1回 | 4回 |
| ダッシュ／するだけ／切り詰め／換算 | 各2回 | 各1回 | 各4回 |
| 同一の強調語・転用動詞 | 1回 | 1回 | 2回 |
| 伝聞エピソード | 1回（検証可能なもの） | 0回 | 1回 |
| 指紋フレーズ・慣用句混交・文体混在 | 0回 | 0回 | 0回 |

## 6. クライアント納品版マニュアルを作るとき（3AC等）

1. 本書の§1〜5を先方の語彙に書き換える（担当者名・社内の呼び名等の内部名は残さない）
2. 先方のCMS・入稿手順・品質チェック体制（誰が・何本・どの基準で）の章を追加する
3. レジスターは「納品」を既定にし、資料規約（人名・金額なし等）は案件RULES.mdから転記する
4. lintスクリプトを先方環境で動かすかは要相談（動かさない場合は§5早見表を目視チェックリスト化して渡す）
5. 納品前に本書 §2〜3 を納品版マニュアル自身に適用する（マニュアルがAI臭かったら台無し）
